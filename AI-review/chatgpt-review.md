
# Анализ пакета `httpq`

## Что это за пакет

`httpq` — это кастомная обёртка над `net/http`, представляющая собой HTTP/RPC client с fluent‑API и поддержкой:

- типизированных ответов (`ResponseModel[T]`)
- логирования (`slog`)
- retry‑политики с backoff
- JSON / XML сериализации
- multipart‑запросов
- context и trace-id

По назначению — внутренний SDK для вызова HTTP‑сервисов (что-то между `resty` и самописным клиентом).

---

## Критические и логические проблемы

### 1. RetryPolicy фактически не работает по умолчанию

Если `RetryStatusCodes` не задан — ретраи **никогда не выполняются**, даже для 5xx.

При этом:
- `DefaultRetryable5xx`
- `DefaultRecommendedRetryStatusCodes`

объявлены, но **нигде не используются**.

❗ Пользователь может ожидать retry, но его не будет.

---

### 2. `panic` в библиотечном коде (ContentMultiPart)

```go
panic(errMarshal)
```

HTTP‑клиент **не должен паниковать**.
Любая ошибка должна возвращаться вызывающему коду.

---

### 3. Ошибки сериализации игнорируются

```go
_ = json.NewEncoder(body).Encode(r.body)
```

Если сериализация упала — запрос всё равно уйдёт, но с пустым телом.
Это критическая логическая ошибка.

---

### 4. Мутация `Rpc` во время выполнения

`r.contentTypeString` изменяется внутри `doOnce`.

Если `Rpc`:
- переиспользуется
- или используется конкурентно

→ возможен **data race**.

---

### 5. `SetTimeout` меняет глобальный `http.DefaultClient`

```go
r.client = http.DefaultClient
r.client.Timeout = timeout
```

Это влияет на **все HTTP-запросы в процессе**.

---

### 6. Retry при валидном HTTP‑ответе

Retry выполняется даже если:
- ответ получен
- тело успешно распарсилось
- статус входит в retry‑лист

Обычно retry делается:
- при сетевой ошибке
- или при неуспешном ответе без бизнес‑данных

---

## Архитектурные и API‑недочёты

### 7. Нельзя отличить пустой ответ от ошибки парсинга

`ResponseModel[T]` не содержит `ParseError`.

---

### 8. Потеря multi‑value HTTP заголовков

```go
map[string]string
```

Теряются:
- `Set-Cookie`
- повторяющиеся заголовки

---

### 9. Multipart реализован упрощённо

Нельзя:
- передавать файлы
- управлять `Content-Disposition`
- задавать mime‑типы

По сути — это не полноценный multipart.

---

### 10. Логирование бинарных тел

Тело запроса логируется как `string`, что опасно:
- для бинарных данных
- для больших payload

---

## Прочие замечания

- Нет дефолтного HTTP‑метода
- Нет `User-Agent`
- Нет jitter для retry
- Странный API `traceID ...string`
- Нет кастомных декодеров

---

## Что сделано хорошо

- Fluent API
- Generics (`ResponseModel[T]`)
- Retry + backoff (идея)
- slog + structured logging
- Context support
- Clone()

---
